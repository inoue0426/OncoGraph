# Homepage knowledge-graph statistics (Issue #12)

`web/data/stats.json` is a small, machine-readable summary of the deployed
graph's scale and composition, shown as compact cards near the top of the
public homepage (`web/index.html`, `#stats`). It is generated by
`scripts/build_static_site.py` from the exact same SQLite export used to
produce `search-index.json`/`relations.json` -- never hand-maintained.

## Schema

```json
{
  "generated_at": "2026-09-17T21:55:25Z",
  "graph_version": "2026-09-17T20:34:16Z",
  "entities": {
    "drug": 908,
    "gene": 45054,
    "disease": 1290,
    "trial": 8892,
    "go_term": 38092,
    "total": 94236
  },
  "relations": 88032,
  "evidence_records": 88032,
  "sources": 5,
  "paths": {
    "benchmark_gold": 7,
    "total": 7
  }
}
```

- `entities`: canonical entity counts by type (the DB's enum member name,
  lowercased -- e.g. `"DRUG"` -> `"drug"`). Only types actually present in
  the current export appear here; a type with zero entities is omitted
  rather than emitted as `0` (see "Never fabricated" below). `entities.total`
  is the sum, i.e. every canonical Entity row regardless of type.
- `relations`: total Relation rows (directed edges). Kept distinct from
  entity counts and from evidence counts.
- `evidence_records`: total Evidence rows across all relations -- a single
  relation can carry more than one (e.g. two sources independently
  supporting the same `indicated_for` edge), so this is not the same number
  as `relations` in general (it happens to match in the current snapshot,
  where almost every relation has exactly one evidence row).
- `sources`: count of *distinct* `evidence.source` values actually present
  in this deployed snapshot -- reflects real coverage of the scheduled
  refresh pipeline, not the full adapter registry (several adapters, e.g.
  Reactome/CIViC/DGIdb/OncoKB/drug_response, are not wired into
  `refresh-data.yml`; see `docs/BIOLOGICAL_SOURCES.md`).
- `graph_version`: the latest per-adapter `--release` label found in any
  evidence row's `context.release` (set from `refresh-data.yml`'s run
  timestamp). Omitted if no evidence row carries one.
- `paths`: **only present when an explicit, stored/curated path artifact
  exists.** See below -- this is never the count of all possible graph
  traversal paths.

## Path-count semantics

"Paths" means an explicit, stored/curated path record -- something a human
or a benchmark curated and checked in, not a traversal computed at query
time. `oncograph.query.traverse()`'s BFS `paths` field (documented in
`docs/QUERY_API.md`) is exactly the latter: ephemeral, query-dependent,
and never persisted -- it is not counted here.

Two such record kinds exist:

- **`paths.benchmark_gold`**: one `BenchmarkItem.gold_evidence_path` entry
  in the versioned benchmark suite (`data/benchmarks/**/*.json`, see
  `docs/BENCHMARKING.md`) -- a curated, checked-in evidence chain used for
  grading a retrieval strategy. Counted across every version directory
  (`v1`'s 9 hand-written items, 7 with a non-empty path; `v2`'s
  programmatically-generated items, all with one -- see
  `docs/BENCHMARK_RUN_v2.md`), so this number grows as more benchmark
  files are added. `read_benchmark_gold_paths()` deduplicates by
  `(version, item id)` in case a curated item is ever repeated across
  files, and skips any non-item JSON artifact under `data/benchmarks/`
  (e.g. `run_benchmark.py`'s results logs, a single JSON object rather
  than a list of items).
- **`paths.mechanistic`** (Issue #10): one `implicated_in_mechanism_for`
  relation from the DrugMechDB adapter (`sources/drugmechdb.py`) -- each
  such relation carries its *entire* curated drug -> mechanism -> disease
  chain in its evidence `context`, not just a single edge, so it is a real
  stored path record, counted directly from the deployed relations export
  (`count_mechanistic_paths()`), not a traversal.

Neither is ever hard-coded; both are re-derived on each build, and
`paths.total` is their sum whenever more than one kind is present.

If no benchmark file exists (or none of its items have a path), the
`paths` key is omitted from `stats.json` entirely -- the homepage then also
omits the "Paths" card, rather than showing `0` or a misleading count.
Once #10/#11 or a future export produces a real mechanistic/evidence-path
artifact, `read_benchmark_gold_paths` (or a sibling reader) should be
extended to add a `mechanistic`/`evidence` key alongside `benchmark_gold`
and roll it into `paths.total`.

## Never fabricated

`compute_stats()` only emits a category backed by real, present data:

- No `"paper"` (Publication) key when no Publication entity exists in the
  deployed snapshot (true today -- the Europe PMC adapter isn't wired into
  `refresh-data.yml`; see `docs/PUBLICATIONS.md`).
- No `"pathway"` key when no Reactome Pathway entity exists in the deployed
  snapshot (true today; only `go_term` currently represents biological
  processes/pathways in the deployed graph -- see `docs/BIOLOGICAL_SOURCES.md`).
- No `"paths"` key at all when no curated path artifact exists.

## Frontend behavior (`web/app.js`)

`renderStats()` reads `data/stats.json`. If that fetch fails or 404s, it
falls back to `computeClientSideStats()`, which recomputes entity/relation/
evidence/source counts from the same `search-index.json`/`relations.json`
already fetched for search (never hard-coded) -- only `graph_version` and
`paths` are unavailable in that fallback, since they need data
(`evidence.context.release`, the benchmark suite) not shipped to the
browser.

Large counts are compact-formatted in the UI (`45.1k`, `94.2k`) via
`formatCompact()`; the exact integer is always in `stats.json` and in each
card's `title` attribute (tooltip/accessible text). Clicking an
entity-type card (e.g. "Drugs") lists all entities of that type directly,
via `renderTypeListing()` -- bypassing the search-intent grammar, which has
no "list every X" form of its own.
