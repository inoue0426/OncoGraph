# Ask OncoGraph: source-backed questions and optional AI

The [public question interface](https://inoue0426.github.io/OncoGraph/#ask) matches literal entity names/identifiers in a bounded published snapshot. It lists connected relationships and up to three underlying source records per relationship (12 relationships maximum). **Find records only** performs retrieval without a model. When available, **Ask AI** sends your question and up to eight prioritized displayed public records to Cloudflare Workers AI; a broad question may use fewer to avoid filling the answer with repetitive links. The response cites the record IDs below it. Broad “best drug” questions get a fixed explanation of why these records cannot rank treatments; they do not send a model request. No patient information should be entered. Cloudflare's free allocation can run out, and the AI response is not checked against every original source. The optional Ollama connection runs from your own computer (see below). “Copy records as prompt” copies the question and selected records for use with a model of your choice; pasting that prompt elsewhere may disclose the question to that service.

## Hosted explanation

The public UI calls `https://oncograph-ask.inoue-yoshitaka-iv1.workers.dev/ask` only after a question matches source-backed records and the visitor requests an explanation. The [Worker source](../cloudflare/oncograph-ask.mjs) needs a Workers AI binding named `AI` and a rate-limiting binding named `RATE_LIMITER` (for example, namespace `1001`, limit `3`, period `60` seconds). It uses `@cf/meta/llama-3.1-8b-instruct-fp8`; GET `/` returns `{ "status": "ready" }` only if both bindings exist. It accepts a JSON POST with `question` (up to 500 characters) and `records` (1–8 objects), and returns `{ "answer": "…", "recordsUsed": 8 }`. The Worker is hosted independently of GitHub Pages, which cannot execute the model. A successful health check establishes only that the endpoint is configured; model inference can still fail. The public snapshot is still searched in the browser, and a model explanation never replaces the displayed records or source links. The Worker restricts request size and rate limits inference; Cloudflare's per-location limiter is approximate, so it does not guarantee a daily quota. Browser Origin checks alone are not access control.

### Update the manually deployed Worker

After a change to `cloudflare/oncograph-ask.mjs` is merged, GitHub Pages does **not** update the Worker automatically:

1. Open [the current Worker source on GitHub](https://github.com/inoue0426/OncoGraph/blob/main/cloudflare/oncograph-ask.mjs), select **Raw**, and copy the entire file.
2. In the Cloudflare dashboard, open **Workers & Pages** → **oncograph-ask** → **Edit Code**. Replace the existing script with the copied file and select **Deploy**. Edit the existing Worker so its `workers.dev` URL remains the same. Keep its existing `AI` and `RATE_LIMITER` bindings.
3. Open [the Worker status URL](https://oncograph-ask.inoue-yoshitaka-iv1.workers.dev/) and confirm `{"status":"ready"}`. This confirms the bindings, not the script version. To verify the new behavior, open the [question interface](https://inoue0426.github.io/OncoGraph/#ask) after Pages finishes publishing. A broad “best drug” question should explain the evidence limit without listing drugs as recommendations; source records should remain below it.

For broad treatment questions, the site gives a fixed explanation of why subtype, stage, tumor biomarkers, and prior treatment matter. It explains that a variant is a difference from a reference DNA sequence; tumor-acquired and inherited changes require separate interpretation. This is general background, not evidence of any individual's variant status. For other questions, the model may add a short genetics explanation, but record-backed claims must cite displayed [R] IDs. See the [NCI explanation of biomarker testing](https://www.cancer.gov/about-cancer/treatment/types/biomarker-testing-cancer-treatment) for the general background.

## Ask from GitHub Pages with your own Ollama

This is for using **your own computer's model in your own browser**, without running OncoGraph's Python server or a Cloudflare Tunnel. Each visitor connects to their own `127.0.0.1:11434`; this does not give other visitors access to the owner's computer. It needs a one-time, exact-origin permission on Ollama and may require browser permission for local network access. Browser compatibility varies. The direct Ollama panel is shown when hosted AI is unavailable; if hosted AI is running and you want to use your own model, use the local server in the next section.

1. Install Ollama, run `ollama pull gemma3:4b`, and keep the normal Ollama desktop app running. Keep Ollama bound to its default loopback address; **do not tunnel port 11434 or bind it to `0.0.0.0`**.
2. In Windows Settings, search for **environment variables**. Open **Edit environment variables for your account**, create a user variable named `OLLAMA_ORIGINS` with the exact value `https://inoue0426.github.io`, and save it. Quit Ollama from the Windows tray and relaunch it from the Start menu so it reads the new variable. This grants scripts served from that origin browser access to the Ollama API; use only an origin you trust. If an existing `OLLAMA_ORIGINS` value is present, preserve the required entries and add this origin rather than replacing them.
3. Open [Ask OncoGraph](https://inoue0426.github.io/OncoGraph/#ask) **on the same computer**. Enter a question and press **Find records only**, open **Use my own Ollama (setup needed)**, then press **Explain with my Ollama**. If the browser asks to allow this site to reach a local device, allow it. **Find records only** never sends a model request.

If it reports that Ollama cannot be reached, check that `http://127.0.0.1:11434/api/tags` opens in the same browser, that Ollama was restarted after changing `OLLAMA_ORIGINS`, and any local network permission prompt. A browser may still block cross-origin loopback requests; the same-origin local server below remains an option. Questions and selected source records are sent to your local Ollama API after you press **Explain with my Ollama**. The page itself is served by GitHub Pages, so code changes on that origin can affect future browser requests to your Ollama API. Do not enter patient-identifying information.

## Optional local explanation, no API key

You can also serve OncoGraph locally through its bounded bridge. The local browser interface and the bridge run on the **same origin**. GitHub Pages cannot call this bridge across origins: it has no CORS allowance and rejects mismatched/missing Origin headers. The default bridge accepts only loopback Host headers. The bridge calls only Ollama on `127.0.0.1:11434`. Keep both services bound to loopback.

1. Install [Ollama](https://ollama.com/) and download a compatible local model, for example `ollama pull gemma3:4b`. Model downloads use storage and local compute. A different model can be selected with `ONCOGRAPH_OLLAMA_MODEL`.
2. From the repository root, install `pip install -e .` and copy the public static data with `python scripts/download_public_snapshot.py`. This copies `search-index.json`, `relations.json` and `stats.json` into `web/data/` and verifies their format. It is a snapshot, not live source queries. Alternatively, build these files with `python scripts/build_static_site.py` after importing your own local SQLite database.
3. Run `uvicorn oncograph.local_ask:app --host 127.0.0.1 --port 8765`. Open `http://127.0.0.1:8765/` in the **same browser and computer**. Press **Ask AI** for retrieval and a model-generated summary, or **Find records only** to retrieve without a model request.

The model receives the question and the **displayed** source records only after that click. Source material is treated as untrusted input to the model; the answer is labeled model-generated and displayed separately from the source records. It can still hallucinate, follow a malicious instruction embedded in data, or misunderstand a CIViC profile. The site does not verify every model claim. Always open original source links. The local bridge does not include API keys, does not query external model services, and does not save a chat history. Ollama itself runs as a separate local process with its own settings.

## Coverage and limitations

- Matching is case-insensitive but literal. It does not reliably resolve synonyms, arbitrary phrasing, or implied concepts. A no-match result means only that this bounded snapshot and matcher did not find a literal entity reference. Once an entity matches, a deterministic heuristic prioritizes the relationship type named in the question (for example, drugs or expression). For broad questions it selects different relationship types before filling remaining slots; this is relevance ranking, not a clinical evidence grade.
- At most eight entity matches and 12 relationships are displayed, with up to three source items per relationship. The AI uses at most eight prioritized relationships. Broad questions prioritize links between two named entities and include at most two links per relation type in the model context; remaining links appear in the source list. Questions that specify drugs, trials, variants, expression, or other relation types prioritize that type instead. This is **not** an exhaustive retrieval or a validated retrieval benchmark.
- CIViC evidence direction, resistance, and contradictions are retained in the displayed records. FDA labels and CIViC Assertions are not integrated. A gene path, trial record, or approved-stage indication is not itself a US approval or treatment recommendation.
- Browser permission policies for a public site calling `localhost` differ across browsers. Direct Ollama access needs an exact `OLLAMA_ORIGINS` allowance; the optional OncoGraph bridge uses its own same-origin UI instead of permitting cross-origin API requests. Pages remains a free, static evidence viewer and prompt exporter when a model is not configured.
